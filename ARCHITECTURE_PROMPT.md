## Задание

Ты — ведущий full-stack разработчик команды HackAlem AI. Реализуй полный, работающий MVP **Career Quest**: сотрудник видит профиль и карьерную траекторию, получает объяснимые AI-рекомендации, отмечает выполнение активности и видит изменение навыков; HR видит дефициты компетенций и участие сотрудников.

Результат — запущенное и проверенное приложение. Разрабатывай вертикальными сценариями, соединяя интерфейс, API, бизнес-логику и данные на каждом этапе. Не останавливайся на каркасе, плане или отдельных несвязанных модулях.

### 3. Архитектура и стек

Используй **модульный монолит** в одном репозитории:

- Backend: Python, FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL.
- Frontend: TypeScript в строгом режиме, Next.js с App Router.
- Redis: короткоживущий кеш рекомендаций и при необходимости HR-сводки. Его отказ не должен мешать чтению профиля и сохранению выполнения.
- Docker Compose: `web`, `api`, `postgres`, `redis`. Единственное backend-приложение владеет бизнес-логикой. Next.js отвечает за интерфейс.
- Используй совместимые стабильные версии и фиксируй зависимости. Подходящий исходный вариант контейнеров — Python 3.12 и Node.js 22; сверяй ограничения выбранных пакетов. Не используй плавающий тег `latest`.
- Один AI-компонент внутри backend. Для MVP достаточно официального SDK и структурированного ответа; отдельный framework агентов не требуется.

Схема взаимодействия: `браузер → Next.js → /api/v1 → FastAPI → PostgreSQL / Redis / OpenAI API`.

Предусмотри единый origin через проксирование `/api` из Next.js в backend. Адрес `api` внутри Compose не должен попадать в браузер как публичный URL. Frontend не подключается к PostgreSQL и не вызывает модель напрямую.

```text
backend/

    main.py
    core/                     # конфигурация, БД, Redis, безопасность, часы, ошибки
    features/

      development/            # история, навыки, разрывы, допуски, выполнение
      recommendations/        # AI, схемы ответа, проверка, кеш, журнал запусков
      hr_analytics/           # агрегаты и списки для HR
      data_import/            # начальная загрузка и импорт JSON/CSV
  migrations/
  tests/
frontend/
  src/
    app/                      # страницы и композиция фич
    features/
      auth/
      employee-profile/

      activities/
      recommendations/
      hr-analytics/
      data-import/
    shared/
      api/                    # клиент и типы контрактов
```

Внутри backend-фичи используй `router.py`, `schemas.py`, `service.py`, `repository.py`, `models.py` по необходимости. Не создавай пустые слои и универсальный CRUD-framework ради структуры.

Правила переиспользования:

1. `development` — единственное место расчета текущих навыков, цели, разрывов, прогресса, допустимости и эффекта активности. Это преимущественно чистые функции с явными входами и выходами.
2. `recommendations` и `hr_analytics` используют эти функции. Frontend отображает результаты API, не воспроизводит формулы на TypeScript.
3. `catalog` и `employees` не зависят от рекомендаций и HR. Направление зависимостей: каталог/профиль → развитие → рекомендации/аналитика. Импорт координирует загрузку через явные интерфейсы хранения.
4. Между фичами используй сервисы и типизированные структуры. Не вызывай чужие роутеры и не копируй запросы к данным в разные экраны.
5. `core` содержит только инфраструктуру, `shared/ui` — реально повторяющиеся компоненты. Предметная логика остается у владельца фичи.

### 4. Датасет и хранение

Фактически изученный набор: **200 сотрудников, 40 активностей, 60 навыков, 32 профиля ролей/грейдов, 2 743 записи истории**. История охватывает 2024-10-01–2026-09-30. Все исходные ссылки и идентификаторы согласованы.

- `employees.json` имеет корень `{meta, employees}`, `events.json` — `{meta, events}`, `skills.json` — `{meta, proficiency_scale, skills, role_profiles}`. Не ожидай голый массив вместо этих объектов.
- `meta.as_of_date = 2026-10-01` — расчетное «сегодня» датасета. Используй его для доступности сессий и бизнес-расчетов. Реальные системные часы применяй для длительности запросов, TTL и служебных временных меток.
- Колонки истории: `record_id, employee_id, event_id, date, due_date, status, completion_pct, score, feedback_rating, assigned_by`.
- Пустые `due_date`, `score`, `feedback_rating` означают отсутствие значения. Не преобразуй их в нули.
- `employees.skills` — базовые уровни на `last_review_date`. После нее в наборе есть **318 завершенных участий**, которые еще требуется учесть.
- У **66 сотрудников** цель отсутствует, у **28** цель предполагает другую роль. Не своди все цели к повышению в текущей роли.
- Обязательны `EV_001`–`EV_004`; повторное прохождение после завершения разрешено только для `EV_036`.

Храни исходные ID как строки, без привязки к диапазону E0001–E0200: проверочные профили могут иметь новые ID. JSONB подходит для словарей навыков, требований и характеристик события; не дроби их на десятки таблиц.

Минимальные сущности: сотрудники, каталог навыков, профили ролей, активности, записи участия, демонстрационные пользователи, результаты рекомендаций, состояние датасета с `as_of_date` и ревизией. История и завершения — в PostgreSQL. Redis не является источником истины.

Начальная загрузка идемпотентна: повторный запуск не дублирует записи и не сбрасывает импортированные профили или действия пользователя. Сохраняй базовые оценки отдельно от вычисленных уровней.

### 5. Общие правила развития — реализовать до AI

**Текущие навыки.** Отсутствующий навык равен 0. Начни с базовой оценки, затем последовательно примени только завершенные участия после `last_review_date`, в порядке `(date, record_id)`. Остальные статусы не дают прироста. Одно участие учитывается один раз.

Для каждого развиваемого навыка применяй:

```text
new_level = max(current_level, min(5, max_level, current_level + gain))
```

Внешний `max` необходим: активность с низким потолком не должна уменьшить уже имеющийся уровень. Обязательные активности исключаются из рекомендаций, но их фактический вклад в историю учитывается по тем же правилам. В частности, `EV_004` имеет развиваемые навыки.

**Неоднозначность исходной истории.** Для self-paced `date` означает зачисление, отдельной даты завершения нет. Для импортированных строк `completed` используй `date` как доступное приближение даты учета и явно опиши это допущение в README. Не выдавай его за известную дату завершения. Для новых действий храни отдельную дату учета в предметной модели и реальную служебную метку; не сравнивай случайно реальное 23 сентября с виртуальным 1 октября.

**Цель.** Используй заданные `career_goal.target_role/target_grade`, включая смену роли. При `null` прими явное MVP-допущение: следующий грейд текущей роли, порядок Junior → Middle → Senior → Lead. Для Lead без цели показывай поддержание текущих требований; не выдумывай следующий грейд. Показывай пользователю, когда цель выбрана автоматически.

**Разрывы и прогресс.** Разрыв — `max(0, required - current)`. `critical_skills` выделяй отдельно. Простой показатель соответствия цели: `100 × sum(min(current, required)) / sum(required)` по ее требованиям, с защитой от нулевого знаменателя. Это прозрачное MVP-решение, не формула из ТЗ. Рост навыков не повышает грейд сотрудника автоматически.

**Допустимые активности.** Общая функция проверяет обязательность, текущую роль и грейд, prerequisites по пересчитанным навыкам, завершения, доступность сессий относительно `as_of_date` и реальный полезный прирост для цели. Для self-paced пустое расписание допустимо. Карьерная цель в другой роли сама по себе не дает допуск к событиям этой роли. Исторические участия не переоценивай по текущему допуску: они могли соответствовать предыдущему грейду.

Исключай уже завершенные активности, кроме `EV_036`. Для начатой подходящей активности допускай рекомендацию «продолжить», не создавая дубликат участия. Учитывай случаи, когда прирост помогает выполнить prerequisite полезного следующего шага; не требуй длинного планировщика. Если прямых кандидатов нет, проверь такие подготовительные шаги на глубину один и объясни их связь с целью.

**Завершение.** Повторно проверь права и допустимость действия. Сохрани участие атомарно, пересчитай состояние, верни измененные навыки и прогресс. Защити от повторного HTTP-запроса и параллельного двойного завершения ограничениями БД/идемпотентностью. Для регулярного клуба различай отдельное участие и повтор запроса к тому же участию. Не записывай одновременно прибавку в базовые навыки и в историю для повторного воспроизведения.

Отметка в интерфейсе — пользовательское подтверждение выполнения в синтетическом демо. Не утверждай, что приложение проверило реальное прохождение внешнего курса. Для будущих сессий обычный режим должен учитывать расписание; демонстрируй выполнение на доступной self-paced активности или введи явно обозначенную симуляцию, не меняющую исходные даты скрыто.

### 6. AI-навигатор рекомендаций

Реализуй один ограниченный цикл: **цель → сбор фактов → допустимые варианты → выбор AI → проверка → сохранение плана → наблюдение за новым состоянием после выполнения**. Оркестратор использует функции `get_development_context`, `list_eligible_events`, `estimate_event_gain`, `validate_recommendation`. Названия можно адаптировать, сохраняя ответственность.

На одну рекомендацию достаточно одного запроса к модели. Допуски и арифметику проверяет код; AI выбирает и упорядочивает подходящие шаги, учитывая комбинацию факторов. Не подменяй выбор модели заранее выбранным единственным событием, для которого модель лишь пишет красивый текст.

Передавай модели:

- роль, грейд, стаж, явную или выбранную цель;
- текущие навыки, требования цели и критические разрывы;
- релевантную историю, включая завершения, no_show, dropped, declined и оценки;
- компактный список всех допустимых кандидатов, условия участия и вычисленный прирост;
- формат и трудоемкость активностей, если они помогают объяснить выбор.

Не отправляй имена и весь массив сотрудников, когда достаточно одного обезличенного профиля. Описания и импортированные строки обрабатывай как данные, а не инструкции модели. Из неявок не делай недоказанных выводов о личности или причине отказа. Предпочтительный язык сотрудника не доказывает язык проведения курса: такого поля в событиях нет.

Структурированный ответ проверяй Pydantic-схемой: список из 1–3 уникальных `event_id`, порядок, краткое объяснение и ссылки на факторы/факты. Допускай пустой список с конкретной причиной, когда подходящих активностей действительно нет. Не дополняй список фиктивными событиями до трех.

Для каждого рекомендованного шага покажи минимум **три разные группы факторов** из: текущий грейд, разрыв навыков, история участия, требования следующего/целевого уровня. Предпочтительно использовать все четыре. Числа, ID и прирост подставляй из проверенных данных; убедись, что explanation ссылается на факты именно этого сотрудника. «Истории нет» — корректный факт для нового профиля; выдуманные прошлые успехи недопустимы.

Показывай отдельно расчетный эффект, например `System Design 2 → 3, требование цели 4`. При нескольких рекомендациях это независимые эффекты относительно текущего состояния, если явно не построена последовательность. Не складывай их с превышением потолка навыка.

Предпочтительный API — официальный OpenAI SDK, Responses API и Structured Outputs, если выбранная доступная модель это поддерживает. Имя модели, ключ и при необходимости адрес API — серверные переменные окружения. Подтверди совместимость небольшим реальным запросом; не считай наличие `.env` доказательством работающего API.

Сделай общий deadline запроса меньше 10 секунд, оставив время на БД и проверку. Отключи повторные попытки SDK, которые нарушают этот бюджет. Обрабатывай таймаут, отказ модели, лимит API и невалидный ответ.

При сбое верни проверенный многокритериальный резервный подбор и явно укажи `source: fallback` с понятным сообщением. При успехе — `source: ai`. Отсутствие ключа не должно ломать профиль, историю и HR. Резервный режим обеспечивает доступность, но **не заменяет обязательную проверку реального AI** перед сдачей.

Храни результат, версию промпта, модель, длительность, ревизию данных и источник ответа. Кешируй по сотруднику, ревизии и конфигурации модели/промпта; после импорта и выполнения старые рекомендации неактуальны. Если ревизия изменилась во время AI-вызова, не сохраняй ответ как актуальный: верни понятное состояние для повторного запроса. Ошибка Redis означает работу без кеша.

Показывай только фактические высокоуровневые действия и подтверждающие факты, без скрытых рассуждений модели. Не рисуй фиктивные вызовы инструментов и не требуй streaming ради анимации.

### 7. Контракты API и экраны

Зафиксируй Pydantic-контракты и OpenAPI до параллельной работы над зависимыми фичами. Используй единый формат ошибок с `code`, `message` и деталями валидации. Frontend получает типы из OpenAPI или из явно синхронизированных контрактов; API-вызовы идут через один клиент.

Минимальный набор маршрутов под `/api/v1`:

| Метод и маршрут | Назначение и доступ |
| --- | --- |
| `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` | Демонстрационные учетные записи и серверная проверка личности |
| `GET /employees` | HR: список и поиск сотрудников |
| `GET /employees/{id}` | Свой профиль или просмотр HR |
| `GET /employees/{id}/development` | Навыки, цель, разрывы, прогресс и допустимые следующие шаги |
| `GET /employees/{id}/history` | История участия с данными активности |
| `GET /employees/{id}/recommendations` | Последний результат и его актуальность |
| `POST /employees/{id}/recommendations` | Получить актуальный AI-подбор, использовать подходящий кеш |
| `POST /employees/{id}/activities/{event_id}/complete` | Завершение своего участия, идемпотентность, измененное состояние |
| `GET /hr/overview` | HR: дефициты, отсутствие шага, участие |
| `POST /hr/import` | HR: импорт профилей и/или истории |
| `GET /health`, `GET /ready` | Состояние сервиса; отказ необязательного кеша/AI не равен падению БД |

HR может читать произвольного сотрудника и получать для него рекомендацию. Изменение выполнения от имени сотрудника не включай в HR-права без отдельного обоснования. Проверяй доступ на backend у каждого маршрута; скрытой кнопки недостаточно.

Сделай простой вход с подготовленными аккаунтами сотрудника и HR и готовой библиотекой подписанной HttpOnly session-cookie. Роль и связанный сотрудник определяются сервером, а не полями запроса. Подпись, срок жизни, SameSite и проверка origin для изменяющих запросов; HTTPS Secure-cookie в развернутой среде. Пароли хешируются, секреты задаются конфигурацией. Не разрабатывай регистрацию, восстановление пароля и корпоративный SSO.

Экраны:

1. **Вход.** Понятные демонстрационные роли, сведения о доступах в README, отсутствие публичного переключателя в HR без проверки.
2. **Профиль сотрудника.** Роль, грейд, цель, навыки, прогресс, критические разрывы и история. Рядом карточки 1–3 рекомендаций: причина, факторы, прирост, формат и трудоемкость, действие выполнения/продолжения.
3. **HR-обзор.** Частые дефициты по количеству сотрудников, список без актуального шага, участие по активностям со статусами, переход в профиль.
4. **Импорт для HR.** Выбор JSON/CSV, результат загрузки или ошибки с указанием строки/поля, переход к импортированному сотруднику.

Не делай вид, что рекомендации уже рассчитаны всем. В HR различай: «нет подходящих активностей», «рекомендация еще не рассчитана», «результат устарел», «актуальный шаг есть». Список без актуального шага должен включать соответствующие причины. Для обзора не запускай 200 AI-запросов; агрегаты считаются локально, индивидуальный расчет запускается по действию пользователя.

После выполнения сразу отобрази фактическое изменение из ответа API, обнови историю и пометь прежний подбор устаревшим. Затем запроси новый подбор, сохраняя доступность страницы. Предусмотри loading, empty и error состояния. Основной язык MVP — русский; исходные названия навыков можно сохранять.

### 8. Импорт, воспроизводимость и доступы

- Поддержи дополнительные `employees.json` и `activity_history.csv` именно в схеме набора, с новыми ID и ссылками на существующий каталог. Оба файла можно загружать совместно; history-only импорт допустим для известных сотрудников.
- Валидируй типы, диапазоны, даты, статусы, роли/грейды, навыки и все внешние ссылки. При ссылке на другого сотрудника из того же пакета проверяй пакет целиком, а не порядок строк.
- Ошибка возвращает понятный отчет без частично примененной загрузки. Повторный импорт тех же ID не создает дубликатов; изменения существующего профиля или записи выполняются предсказуемо, атомарно и отражаются в отчете. Не затирай непереданные локальные участия.
- Несовместимую дату среза явно отклоняй с объяснением; не смешивай разные «сегодня» молча. После успешного импорта увеличь ревизию и пересчитай затронутые результаты.
- Запуск приложения после заполнения документированных настроек — `docker compose up --build`. Миграции и идемпотентная начальная загрузка выполняются автоматически одним назначенным процессом после готовности БД. Несколько API-процессов не должны одновременно создавать схему или seed.
- PostgreSQL использует volume; обычный перезапуск сохраняет данные. Для проверки чистого запуска применяй отдельный временный Compose project/volume, не удаляя рабочие данные пользователя.
- Датасет доступен запуску из репозитория или документированного комплекта сдачи; не полагайся на Downloads и абсолютные пути одного компьютера.
- Подготовь `.env.example`, `.gitignore` и `.dockerignore`; настоящий `.env` не перезаписывай и не включай в образ. Пример содержит названия и безопасные значения, без реальных ключей.
- README описывает запуск, переменные, архитектуру, правила роста, все допущения, импорт, API, демонстрационные учетные записи, ограничения и команды проверок. Отдельно перечисли используемые модели, библиотеки и источники данных.
- Ключевая функциональность должна проверяться без личной подписки участника. Нужен подтвержденный способ доступа экспертов к реальному AI: разрешенный демонстрационный сервис или отдельные переданные безопасным способом доступы. Инструкции «введите свой платный ключ» и один fallback не доказывают выполнение этого требования. Если доступ не решен, явно зафиксируй это как блокер сдачи; не встраивай ключ в репозиторий.

### 9. Разделение реализации по фичам

Разделение ниже — зоны ответственности команды до трех человек, а не требование создавать дополнительных AI-агентов. При другом составе объединяй зоны, сохраняя модульные границы.

| Владелец | Фичи и файлы | Результат для других |
| --- | --- | --- |
| A — интеграция и данные | Compose, `core`, `identity`, `catalog`, `employees`, `data_import`, миграции; затем backend HR-агрегатов | Запуск, данные, вход, контракты профиля/импорта, HR API |
| B — развитие и AI | `development`, `recommendations`, их схемы и тесты | Общий расчет, допуски, выполнение, AI-подбор; функции для HR |
| C — интерфейс | Next.js и frontend-фичи, общий API-клиент, пользовательские сценарии | Связанный UI сотрудника, HR и импорта; проверка сценариев в браузере |

За `main.py`, миграции, общие зависимости и корневые конфиги отвечает A; за frontend layout и общий API-клиент — C. Владельцы других фич предоставляют изменения через согласованный интерфейс, не переписывая одновременно общие файлы. Документацию каждой фичи готовит ее владелец; A собирает итоговый README.

Первые договоренности: сущности/ID, форматы ошибок, ответы development/recommendations, выполнение и импорт. Временные UI-фикстуры должны соответствовать контрактам и быть явно помечены; основной путь переводи на реальный API сразу при его готовности. Интеграцию выполняй после каждой фичи, а не в конце.

### 10. Приоритеты и время

**P0 — полный обязательный MVP:** запуск и seed; серверные роли; профиль/история/траектория; корректные навыки; AI-подбор и три фактора; выполнение с сохранением; HR-обзор; импорт новых профилей/истории; обработка основных ошибок; README и проверяемые доступы.

**P1 — после рабочего P0:** усиление качества на сложных профилях, более ясное сравнение «до/после», точная диагностика отсутствия шага, улучшение измеренной задержки, удобный сценарий демонстрации и понятный журнал действий AI.

**P2 — только при запасе времени:** качественная локализация, дополнительная визуальная отделка, экспорт отчета, дополнительные фильтры. Валюта, награды, социальная сеть, менторская платформа, конструктор событий, прогноз увольнений, чат, календарь и мобильное приложение не входят в базовый MVP.

Не добавляй микросервисы, Kafka, Celery, отдельный векторный поиск, обучение моделей, сложную оркестрацию агентов и собственный UI-framework без конкретной необходимости для обязательного сценария.

Ориентир при наличии примерно 4–4,5 часов до дедлайна:

| Время от начала реализации | Цель |
| --- | --- |
| 0–20 мин | Проверка окружения/времени, границы фич, контракты, Compose, загрузка данных, проверка доступности AI |
| 20–65 мин | Первый вертикальный сценарий: вход → реальный профиль → пересчитанные навыки/цель → первая реальная AI-рекомендация |
| 65–120 мин | Выполнение → изменение прогресса → сохранение после обновления; в параллельной зоне UI и проверка прав |
| 120–180 мин | HR и импорт подключены к общим расчетам; новые профили проходят полный сценарий |
| Последние 60 мин | Обязательные пробелы, реальные проверки, холодный запуск, ошибки API, README, демонстрационные доступы |
| Последние 30 мин | Заморозка фич, критические исправления, репетиция, комплектность сдачи |

Эти интервалы адаптируй к фактическому остатку. Если времени меньше, сокращай отделку и P1/P2, а не импорт, права, корректность рекомендаций и запуск. Параллельные зоны команды должны интегрироваться в течение работы. Не считай исходные пять часов заново от момента чтения промпта.

### 11. Проверки и минимальная демонстрация

Автоматическими тестами проверь важную предметную логику и границы:

- базовая оценка + completed после review; завершение до/в день review не начисляется повторно; остальные статусы не дают навыков;
- отсутствующий навык, потолок, отсутствие понижения, обязательная активность с приростом;
- смена целевой роли, отсутствие цели, Lead, critical skills и prerequisites;
- повтор завершенного события, исключение `EV_036`, повтор и конкурентное выполнение одного действия;
- атомарный импорт новых профилей/истории, повторный импорт, неизвестные ссылки и ошибочные значения;
- запрет чужого профиля/HR-импорта для сотрудника, отсутствие секретов в ответах;
- несуществующий event_id от модели, невалидный ответ, таймаут, отказ Redis, устаревание результата после изменения данных.

Создай три дополнительные синтетические проверочные фикстуры, явно обозначив их как свои, а не профили жюри: конфликт минимального навыка с критическим разрывом и историей пропусков; активность с невыполненным prerequisite/потолком; смена роли либо отсутствие истории. Они проверяют многокритериальность и обобщение, не подгонку под известные ID.

Запусти backend-тесты, проверку типов и production build frontend. Затем проверь в браузере и через API реальную связку, включая импорт и сохранение после перезапуска. Отдельно зафиксируй успешный вызов модели, ее фактический результат и измеренную задержку. Тестовый ответ провайдера не считается этой проверкой.

Демонстрация на 2–3 минуты:

1. Открыть сотрудника, показать цель и критический разрыв.
2. Получить реальную AI-рекомендацию, объяснить три фактора и ожидаемый прирост.
3. Отметить доступную активность выполненной, показать изменение навыков и траектории после обновления страницы.
4. Войти как HR, показать дефициты, причины отсутствия шага и участие.
5. Импортировать дополнительный профиль с историей и получить для него рекомендацию без правки кода.

Для готовности нужны: работающий P0 целиком, пройденный запуск по README, проверенные права и импорт, корректный пересчет, реальный AI, результаты проверок и понятные ограничения. Файл с кодом или успешный build сами по себе не означают готовность.

Веди `TASK.md` с состояниями `[ ]`, `[~]`, `[x]`, `[!]` и результатами проверок. В конце сообщи, что реализовано и проверено, точные команды запуска, оставшиеся ограничения, статус реального AI и способ проверки экспертами. Не объявляй проект сданным без фактической сдачи и не выполняй запрещенные пользователем Git-операции.
